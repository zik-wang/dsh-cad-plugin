# 可追溯的图片转 CAD 流程

## 一次任务怎样运行

1. **附件接收**：桌面插件按原生 session ID 绑定任务；读取当前对话未消费的图片附件，保存原图与哈希。普通“继续”复用任务；补图或明确修改形成新修订。图片里的文字指令是文档内容，不替代用户要求。
2. **读图契约**：DSH 读取整页与局部，整理尺寸、公差、视图比例、重复数量和细小尖端等特征，再调用 `cad_contract` 固定待实现特征。辨认不清的关键尺寸需要补充证据。
3. **建模**：DeepSeek 自己编写 Python。通用 `cad_feature` 提供 V 槽等构造算子，不内置 1/2/3 号零件答案。几何模型保持毫米 1:1，纸面放大通过视图变换表达，不能偷改标注比例。
4. **导出与检查**：`cad_python` 执行、`cad_export` 导出 DXF/PDF/PNG，再由 `cad_view` 查看整页与局部。`cad_preflight` 对结构、比例、特征和文件状态做程序检查；通过不等于所有工程语义都正确。
5. **冻结候选**：`cad_review` 对原图、DXF、PDF、预览等建立冻结副本及哈希。报告必须对应同一源图修订和同一候选文件。
6. **独立 DSH 审图**：启动另一个原生 DSH headless 会话读取原图与冻结候选。通过 `cad_submit_review` 提交证据、问题和结论；检查尺寸公差、重复特征、方向基准、几何一致性、比例、可读性和原图完整性。
7. **局部返修**：作者读取报告，修复对应区域与关联视图，重新导出、预检及送审。未修改的候选复用已有结论，不能通过重试把阻塞报告洗成通过。
8. **交付门禁**：只有当前文件哈希、当前修订、通过的预检和通过的原生审核一致时，`cad_deliver` 才生成正式发布目录；否则保留候选及阻塞原因。

## tools 与 Harness 分工

- **DSH 桌面插件层**：`plugin.mjs` / `plugin-v036.mjs` 注册入口、读取附件、绑定会话、注入工作流说明。简易入口额外提供无参数 `cad_start`。
- **工具层**包含 `runtime/tools*.mjs` 的 CAD 工具注册，以及 `host.py`、`cad_features.py`、`cad_pdf_backend.py` 中的读写、导出、几何与测量。
- **Harness 层**：`task-store.mjs` 管理任务修订；`workflow_stage.py` 约束阶段；`review-delivery.mjs` 验证候选/审图/交付状态；`native-review.mjs` 启动独立审图；`cost-control*.mjs` 管理预算。
- **审图记录**由 `review-history.mjs` 保存，包含冻结候选与对应报告。

这套实现使用 DSH 原生工具注册接口。

## 降本机制及边界

降本版与简易入口对一个原生对话的作者和审图共享 10 元估算账本。价格换算系数写在源码里，不是实时拉取的供应商报价；上一次用量回执未结算时会阻止盲重试，并提供历史恢复机制。每个独立审图最多 24 次请求，达到阶段工具预算会要求提交已有证据；每源图修订最多 4 个不同已完成审图候选。输出不再增加旧版额外 maxTokens 限制，服务端自己的限制仍存在。

这降低重复长上下文和无效审图消耗，不保证账单严格不超 10 元，也不保证每张图在预算内达到要求。开发测试与正式作图分开记录；交付检查只读本地文件，不重新消费模型额度。

## 证据如何解读

- 早期流程由 DSH 调用 Codex 编写的零件配方。插件流程由 DSH 自行读图和编写建模程序，再用通用工具导出与审图。
- 用户先后认可过部分图纸；最近一轮候选仍有自动审图未通过的记录。不能用此前人工验收替当前自动门禁盖章。
- 简易入口已验证无图短请求 → `cad_start` → 一句上传提示，以及本地附件续传、复用和隔离逻辑；尚无该新入口完整付费新图回归。
- 自审提高发现问题的机会，程序预检与模型审图也可能漏检；不等价于工程制造签核。
